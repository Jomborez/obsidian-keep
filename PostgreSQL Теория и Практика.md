## 0. Базовые термины

> [!info] Экземпляр (Кластер БД)  
> Это изолированная оболочка со своими паролями, пользователями, базами и т.д. Каждый кластер слушает разные порты, чтобы не конфликтовать с другим, и полностью изолирован.

Логи лежат по пути:  
`sudo cat /var/log/postgresql/postgresql-17-main.log`

Контрольные суммы посмотреть, только когда сервер остановлен:

bash

# Включить подсчёт
sudo ./pg_checksums -e -D /var/lib/postgresql/17/main
# Запросить подсчёт
sudo ./pg_checksums -c -D /var/lib/postgresql/17/main

> [!tip] Переменная ON_ERROR_ROLLBACK  
> Необходима в транзакциях к БД. Когда мы ошиблись в одной команде, у нас перед именем пользователя появляется `!#`, и вся транзакция не будет завершена, её можно будет только прервать (commit). Чтобы этого избежать, можно включить переменную:
> 
> sql
> 
> \set ON_ERROR_ROLLBACK on
> 
> С ней, если мы ошиблись в команде, транзакция продолжится.

В PostgreSQL по умолчанию включён автокоммит для одиночных команд, не начинающихся с `BEGIN;`.

## 1. Архитектура PostgreSQL

При выполнении запроса с клиента сервер, прежде чем отдать результат, проверяет 4 правила:

1. **Синтаксис команды**
    
2. **Правила** (есть ли у вас доступ и существует ли такая таблица)
    
3. **Статистика** (логи, что я отдал клиенту тому-то)
    
4. **Передача самих данных**
    

> [!warning] Журнал WAL  
> В случае сбоя оперативной памяти, потери кэша (например, отключение электричества), из журнала WAL можно восстановить данные.

**Многоверсионность** — наличие нескольких версий одной и той же строки, путём снапшотов. Что интересно, PostgreSQL складывает старые версии и новые в один каталог в ОС.

### Два основных уровня изоляции (всего их 4)

> [!note] Read Committed (работает по умолчанию)  
> Работает так: если одновременно открыта транзакция и один делает запрос `select * from table;`, у него выводится только 1 строчка (например, 52). Но в другой транзакции кто-то добавил ещё строку 66 и закоммитил. При следующем `select * from table;` он уже увидит не 1 строчку, а две, хотя сам ещё не закоммитил.  
> _При удалении таблицы, если кто-то в другой транзакции просматривает её, удалить не получится, пока транзакция не будет завершена на устройстве, которое просматривает._

> [!note] Repeatable Read  
> Главное отличие: пока ты сам не завершишь свою транзакцию, изменения он никакие не увидит. Как только прописал `commit` или `rollback`, он увидит другие изменения.

- **Блокировки** — чтение строк никогда не блокируется.
    
- **Блокировка таблиц** — запрещают изменение и удаление таблиц, пока с ней идёт работа.
    
- Устанавливаются автоматически и снимаются при завершении транзакции, также можно установить вручную.
    
- **Статус транзакции** — активна, зафиксирована, оборвана.
    

**Служебная информация** — хранится на диске `pgexact`, внутри этого каталога файлики по 2 бита, которые показывают статус.

## 2. Очистка

Есть ряд факторов, которые надо периодически делать:

1. **Очистка мёртвых строк** (старые перезаписанные версии, которые не используются).
    
2. **Обновление карты видимости** (чтобы не ходить в таблицу, а смотреть строки по индексам; в таком случае многоверсионность будет сохраняться, и мы будем игнорировать мёртвые строки).
    
3. **Обновление статистики**: показывает актуальное количество строк.
    

> [!danger] Заморозка (Freeze)  
> У каждой транзакции в PostgreSQL есть номер — **XID**. Он 32-битный. Считай, что это счётчик, который постоянно растёт: 1, 2, 3... и у него есть потолок — примерно **4 миллиарда** (реально безопасный предел около 2 млрд).
> 
> Когда счётчик доходит до потолка, он **переполняется** и начинается заново с нуля. И вот тут беда.
> 
> **Заморозка** — это когда PostgreSQL говорит: «Эта строка старая, она была создана очень давно. Забудь про её номер транзакции, считай её **вечной и видимой всем всегда**.» То есть строка как бы получает штамп «сделано до начала времён». Её больше не нужно сравнивать с текущим счётчиком XID — она всегда видима. И переполнение счётчика ей уже не страшно.

Чтобы не делать это ручками (админу это тупо нереально), создали два демона. Один **Autovacuum launcher** — он постоянно висит в процессах, можно на него посмотреть:  
`ps aux | grep "autovacuum launcher"`  
Он запускает **autovacuum worker**, и вот уже он делает ряд задач: очищает таблицы, замораживает, вообщем делает всё выше перечисленное.

## Буферный кэш и журналы

>[!info] Буферный кэш
 Это выделенная оперативная память, которая хранит в себе массив буферов, в стандартной конфигурации PostgreSQL один буфер равен 8 КБ. Нужен этот кэш для ускорения работы БД, чтобы часто не обращаться к диску. Грязные буферы это страницы которые хранятся только на ОЗУ, на диске их ещё нету. В буферном кэше используются блокировки, если 1 процесс изменяет страницы данных, другой процесс одновременно с этим изменять не сможет, только читать.

По умолчанию размер буферного кэша 128 МБ, его всегда нужно увеличивать, если говорить в общем, размер буферного кэша 20-40% от всей оперативной памяти.
Для изменения этого параметра используем: 
```psql
ALTER SYSTEM SET shared_buffers = '2GB';
```

И этот параметр требует перезагрузки экземпляра:  
`bash`
```bash
sudo pg_ctlcluster 17 main restart 
```
 Но рано или поздно даже при большом количестве ОЗУ кэш переполнится, и нам нужно будет какие-то данные переносить из оперативной памяти на диск.
  
  **Когда этот момент наступает, алгоритм вытеснения смотрит к каким данным мы обращались реже всего и переносит их на диск.**

>[!info] Журнал предзаписи WAL  
Буферный кэш хранит страницы данных в ОЗУ, и при сбое питания или аварийном выключении они теряются. Чтобы это исключить, используется журнал предзаписи (WAL): в него последовательно фиксируются низкоуровневые redo-записи об изменениях `не сами данные, а описание «что и куда записать»`. При восстановлении СУБД проигрывает эти записи и восстанавливает согласованное состояние.  
Ключевое правило write-ahead: **запись WAL об изменении страницы должна быть сброшена на диск раньше, чем сама изменённая страница**. Поэтому при COMMIT достаточно сбросить WAL (последовательная запись, group commit) — это быстрее, чем синхронно писать разрозненные страницы. Сами страницы сбрасываются позже, при чекпоинте.   `Пока запись в журнал WAL не поступит на диск, транзакция не получит COMMIT`.

Журнал WAL физически на диске хранится в отдельных файликах на 16 МБ, когда один файл заполняется, создаётся новый и пишется туда. Посмотреть журнал можно запросом:
```psql
SELECT * FROM pg_ls_waldir();
```
Но теперь возникает вопрос, а какое количество записей хранить в журнале, поскольку у нас может быть в буферном кэше , такие данные к которым обращаются постоянно и на диск они до сих пор не ушли, ну если хранить все записи от создания БД и до сбоя, размер самого журнала будет огромный, это считайте вторая БД по месту будет. И при восстановлении уйдёт уйма времени.
>[!success] Контрольная точка
>Это процесс, который периодически сбрасывает все данные которые есть только на ОЗУ  (`грязные буферы`) на диск. Тем самым ограничивая размер WAL журнала необходимого для восстановления

# 1. Конфигурация СУБД

`postgresql.conf` — Основной файл конфигурации определённого экземпляра и версии, находится по пути:  
`/etc/postgresql/<версия>/<кластер>/postgresql.conf`

Если он лежит в другом месте, посмотреть можно внутри БД командой:

sql

SHOW config_file;

При изменении параметров необходимо перечитать конфигурацию:

bash

pg_ctlcluster версия экземпляр reload

> [!info] work_mem  
> По умолчанию это значение 4096 КБ. Этот параметр выделяет лимит на одну операцию, т.е. для лёгких запросов это значение ещё куда ни шло, но тяжелый запрос будет обрабатываться долго. По дефолту лучше ставить 16-64 мб.
> 
> bash
> 
> sudo nano /etc/postgresql/17/main/postgresql.conf
> 
> ini
> 
> work_mem = 16MB

Есть аналог `postgresql.auto.conf`, он имеет выше приоритет чем `postgresql.conf`, и более удобен, он проверяет базовые ошибки. Например:

sql

ALTER SYSTEM SET work_mem = '14MB';

После всех манипуляций не забываем:  
`sudo pg_ctlcluster 17 main reload`

Проверить, что применилось: `SHOW work_mem;`

> [!warning] max_connections  
> Сколько максимальных подключений разрешено к базе, по умолчанию значение 100. Посмотреть можно: `SHOW max_connections;`  
> Изменить: `ALTER SYSTEM SET max_connections = '350';`  
> **Важно:** этот параметр применится только при **перезапуске** экземпляра, при перечитывании он не применится.
> 
> bash
> 
> sudo pg_ctlcluster 17 main restart

## 1.1 Базовая настройка PostgreSQL

Переходим в оболочку psql под суперпользователем:

bash

sudo -i -u postgres psql

К базе также можно подключиться другой командой:

bash

psql -d база -U пользователь -h адрес -p порт

Создадим пользователя и базу:

sql

CREATE USER test WITH PASSWORD 'test';
CREATE DATABASE test_db OWNER test;

- Посмотреть всех пользователей: `\du`
    
- Выходим из оболочки psql: `\q`
    

И подключаемся нужным пользователем:

bash

psql -U test -d test_db -h 127.0.0.1

`-h` — если это не локальная база, указываем IP базы.

# Создание и заполнение таблицы

sql

CREATE TABLE test ( 
    id SERIAL PRIMARY KEY, 
    name VARCHAR (20) NOT NULL, 
    email VARCHAR (50) UNIQUE, 
    age VARCHAR (50), 
    date TIMESTAMP DEFAULT NOW() 
);

Создаём таблицу `test`.

| Команда                        | Пояснение                                                                                                                                                                              |
| ------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `CREATE TABLE test`            | Создаём новую таблицу с именем test                                                                                                                                                    |
| `id SERIAL PRIMARY KEY`        | Столбец id: тип SERIAL (автоинкрементное целое, PostgreSQL сам создаёт последовательность), PRIMARY KEY — первичный ключ, уникальный и не NULL, по нему автоматически создаётся индекс |
| `name VARCHAR(20) NOT NULL`    | Строка до 20 символов, NOT NULL — обязательное поле, пустым быть не может                                                                                                              |
| `email VARCHAR(50) UNIQUE`     | Строка до 50 символов, UNIQUE — все значения должны быть разными (создаётся уникальный индекс), но NULL допускается (и даже несколько NULL — это особенность PostgreSQL)               |
| `date TIMESTAMP DEFAULT NOW()` | Дата-время; если при вставке значение не указано, подставится NOW() — текущий момент времени                                                                                           |

Добавим строки в нашу таблицу:

sql

INSERT INTO test (name, email, age) VALUES ('Иван', 'ivan@example.com', '15');

`SELECT * FROM test;`

> [!warning] В продакшене  
> Не используйте `SELECT *` на больших таблицах, это может перегрузить БД!

# Выборка записей с условиями

`SELECT * FROM имя_таблицы;` — вывести все строки таблицы _(не рекомендуется в проде)_.

`SELECT id, name, email FROM test;` — вывести определённые столбцы.

Добавить условие:

sql

-- Ищем строки, у которых id > 1
SELECT id, name, email FROM test WHERE id > 1;
-- Ищем строку, где имя не равно Bob и одновременно возраст должен быть больше 20
SELECT * FROM test WHERE name <> 'Bob' AND age > 20;
-- Ищем строку, где в поле age диапазон от 10 до 50
SELECT * FROM test WHERE age BETWEEN 10 and 50;
-- Ищем строки, где email начинается с ivan, а дальше не важно.
SELECT * FROM test WHERE email LIKE 'ivan%';

> [!tip] Оператор LIKE  
> Также можно использовать команду `NOT LIKE` — будет искаться всё, кроме `ivan%`.

sql

-- Сортировка по убыванию и вывести только 2 записи
SELECT id, name, age FROM test ORDER BY id DESC LIMIT 2;

# 3.1 Обновление и удаление записей

sql

-- Обновить данные у определённой строки
